## The defects the tests found (they are not in the starter's weakness list)
Both are "check, then insert" races. Sequential tests cannot see them; the two `Concurrent…` integration tests can.
1. **Duplicate usernames.** `POST /api/auth/register` checks `AnyAsync(u => u.Username == …)` and then inserts; `Users.Username` had no unique index. Six simultaneous registrations of one name gave **six `201`s and six rows** (ten rounds, every round). Several accounts with one name is account confusion: login and token mapping (`preferred_username`) take the first match. Fix: `HasMaxLength(32)` (the registration contract; an index needs a bounded type) plus a **unique index** in a new migration `UniqueUsername`, and the register endpoint maps the unique violation (SQL error 2601/2627) to the same `409` as the pre-check.
2. **`500` on a concurrent duplicate like.** `POST /api/blogs/{id}/like` has the same shape; the composite primary key rejected the second insert and the global handler turned it into a `500` (60 of 90 answers in a trial with six parallel requests). Fix: the violation means "already liked": `204`, which is what the sequential path already answers.

Both fixes use `SqlErrors.IsUniqueViolation(DbUpdateException)` (new, in `Data/AppDbContext.cs`). **Schema change:** run `bash docs/init-database.sh` (the migration is applied by `seclab_migrator`). If your development database already contains duplicate usernames the index cannot be created – run `bash docs/reset-database.sh` first. In a real system the migration would need a data clean-up step before the index. The rows were added to `docs/00` as **W16** (fixed in 16) and to the A06 row of the OWASP matrix.

## The reference suite (`backend/tests/SecLab.Api.Tests/Learner/`)
- **`AuthorizationMatrixTests.cs`** – `Access` enum (anonymous, user, admin, owner only, owner or admin, step-up, key read/write/admin), a `Dictionary` of 34 `"METHOD /route"` entries, `Expected(access, caller)`. Layers: inventory (`EndpointDataSource` of `Harness.Services` vs the table, both directions), metadata (`IAllowAnonymous`/`IAuthorizeData` vs the table), fallback policy (`GetFallbackPolicyAsync` contains `DenyAnonymousAuthorizationRequirement`), and a theory of **34 routes × 7 callers = 238 cases**. One fixture builds the host once (the rate limits are lifted with `EnvScope`, the callers and three API keys are created once, objects a route needs are created per case). Two vocabulary decisions: `{id}` routes get real ids (otherwise a `404` happens before the authorization check and "denied" cells would pass for the wrong reason), and `POST /api/auth/login` answers `401` itself ("wrong credentials"), so that one `401` is not read as an authentication failure. "Allowed" means not 401/403 and not 5xx (the crash endpoint is exempted by name). The avatar upload really writes a file; the test deletes it.
- **`OwaspNegativeTests.cs`** – 40 cases: API1 (cross-object edit/delete/read with state checks; unknown ids), API2 (six kinds of bad token via `TestIdp`: `alg=none`, wrong key with the right `kid`, expired, wrong audience, wrong issuer, garbage; uniform login failures; lock-out boundary), API3 (mass assignment on update and registration; a stranger sees exactly five properties), API4 (`429` + `Retry-After`; page bounds; length limits stored nothing), API5 (admin functions, key level escalation, a read key cannot write), API6 (registration flood), API7 (11 SSRF payloads), API8 (headers on 200/401/403/404/500, CORS, no internals in a crash), API9 (deprecation header, unknown version). API10 is not covered: the outbound call cannot be exercised offline (see *Deliberately left open*).
- **`SecurityUnitTests.cs`** – 158 cases, no host: key hash (including a known-answer vector) and ranks, `OutboundUrlPolicy.TryValidate` (24 refused shapes, the 2048 boundary) and `IsPublic` (~50 addresses incl. IPv4-mapped IPv6 and every range from both sides), `AdminNetworkHandler` (CIDR, mapped addresses, empty configuration), `AuditLog.Clean`, `ContentSanitizer` (active content, every allowed tag, schemes, link `rel`), the validation of the contract records through `Validator.TryValidateObject`, `EncryptedStringConverter` (round trip, randomised, wrong purpose / key ring / tampering).
- **`ContractTests.cs`** + `Snapshots/` – 14 samples of real responses (register, login, me, three profile views, friends, blogs v1/v2, created blog, timeline, admin users, key creation/list) reduced to `path → type`; a snapshot comparison with `SECLAB_UPDATE_SNAPSHOTS=1`; the **credential-property invariant** (regex over every leaf property of every sample; exceptions are listed with a comment); a self-test of that regex; a reflection test that the `User` entity's secret properties are exactly the four known ones and none of the response records has them; the **error contract** over 11 error kinds (problem+json, `status`, `title`, `traceId`, `X-Trace-Id`, only the allowed property names, none of `stackTrace`, `Exception`, `Boom`, `Server=`, `System.` …); validation errors name only the failed fields; v1 is a bare array, v2 an envelope.
- **`DatabaseIntegrationTests.cs`** – 9 cases: the suite runs as `seclab_app` with no pending migrations; registration stores a salted hash and the password is nowhere in the database (`DatabaseContains`); a lock-out survives a "restart" (second host, same database) and is lifted by the database row; API key lifecycle (hash length, secret not in the database, `LastUsedAt`, revocation visible to another host); encrypted phone/address; no orphaned likes after deleting a blog; **two concurrency tests**; the database rejects a duplicate key prefix on its own (`IX_ApiKeys_Prefix`).

## Shipped infrastructure (not part of the patch)
- `Step16Support.cs`: `[OwaspApi]`, and `Mutants` – fault injection through `ConfigureTestServices` (decorators for `IAuthorizationService`, `IAuthorizationPolicyProvider`, `EndpointDataSource`; startup-filter middleware that rewrites bodies or strips headers; `PostConfigure<RateLimiterOptions>`). `TestIdp.Host` calls `Mutants.Apply`; with `SECLAB_MUTANT` unset nothing changes. Only hosts built through `Harness` are affected (tests that create their own `WebApplicationFactory` are not mutated – the pitfall to know).
- `Harness.Services`: the services of the host the clients talk to.
- `Step16TestingTests.cs` (`Kind=Meta`): structure checks. They read the learner's types by reflection (traits, `[OwaspApi]`, constructor parameters) and the learner's source files by regular expression. **They can be gamed** – a test without assertions satisfies every structural check. That is what the mutants and Stryker are for; the checks only keep the suite complete and consistent.
- `docs/attack-scripts/16-mutants.sh`, `16-mutation.sh`, `16-supply-chain.sh`.
- Part 2: `docs/part2-azure/P2-02…`, its solution notes, `README` and `solutions/p2-02-pipeline/ci.yml` were made consistent: unit tests first, the SQL Server tests against a database set up by the repository's own scripts (a GitHub service container cannot mount the pinned certificate and the step-15 tests refuse `TrustServerCertificate=True` – the old example with `sa` and `TrustServerCertificate=True` was already stale after step 15), Stryker as a manual/weekly job with the report as an artifact.

## Deliberately left open
- **API10 / consumer-side contracts.** The only outbound call is the link preview; the connect-time check (step 09) refuses loopback, so a local fake upstream cannot be used, and a test against the real internet would be flaky and slow. Pact-style consumer contracts for the `ExternalApi` project were not written. (The step-08 and step-09 notes that promised "Pact tests per version" and "contract tests reuse `IHttpClientFactory`" are only partly met: the response shapes per version are pinned, the outbound client is not.)
- **The login response still contains `token` = the user id**, a leftover from before step 03 ("WEAKNESS (until step 03)" in `Api.cs`). The contract test lists it as a documented exception; the snapshot records it. Removing it needs the front end to stop reading it. The invariant test is how this was found.
- **Mutation testing covers only pure helpers.** Handlers and endpoints would need the integration tests (minutes per run, shared database). The eight mutants are controls chosen for this app; others (login limiter, CORS, API-key levels, step-up, the admin-network check on its own) have tests but no mutant.
- **Tests share one growing database** and never clean up (unique names instead); no data-reset between runs; parallel execution is disabled assembly-wide.
- **xunit 2.x is deprecated (Legacy)**; moving to xunit.v3 (and the Microsoft Testing Platform) is a separate piece of work.
- **No OpenAPI document**, hence no API-description diffing; snapshots are hand-made (Verify/approval libraries would give nicer diffs).
- **Matrix cases use `{}` bodies**; a route's behaviour with a *valid* body (beyond "not 401/403/5xx") is the business of its own tests (steps 05–11).
- **Fuzzing, DAST in CI, load tests, browser tests**: out of scope (P2-05 has the ZAP baseline).
- **Structural checks can be satisfied by weak tests** (above); a reviewer, the mutants and Stryker are the real gate.
